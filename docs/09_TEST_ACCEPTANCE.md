# 09 검수 기준 및 자동화 테스트
## 단계별 게이트
P0 명세: 모든 API 요청·응답 예시, DDL, 데이터 사전, 화면 데이터 매핑, 원본과 충돌 목록 작성.
P1 수집: 최소 각 핵심 도메인에 실제 출처 데이터 적재, source manifest/라이선스 기록, 중복/누락 보고, 재실행 idempotent.
P2 DB: FK 위반 0, 필수키 누락 0, 유효하지 않은 좌표 표시 0, 카운티 benchmark 혼합 0, schema migration 반복 실행 성공.
P3 API: 모든 endpoint의 성공/400/404/409/500 케이스, pagination, SQL injection 방지, 필터·정렬 일치, 0건 응답.
P4 분석/보고: BFS cycle/방향/3-Hop 제한, 미검증 표시, 3종×3포맷 출력, 과거 재연 분리, 엔진 교체 계약.
P5 UI: 8개 화면·관리자, 로딩/빈/오류/부분 성공, 모든 버튼 실제 동작, 필터 동기화, 지도/네트워크 상호작용, 390/768/1024/1440px 스크린샷 검수.
P6 통합: 수집→정제→검색→분석→보고서 전체 E2E; 업로드 실패 롤백; 데이터 소스 갱신 후 검색 인덱스 갱신.
## 성능(목표, 측정 전)
100,000+ **합성 성능 테스트 레코드**(실데이터와 분리), 일반 검색 P95 ≤1초, 집계 API P95 ≤2초, 초기 화면 주요 콘텐츠 ≤3초. 환경 사양·동시성·쿼리·데이터 분포를 기록하고 실제 결과와 목표를 구분. 300k 이상 추가 시험 권장.
## 시각 검수
스크린샷 기반 정렬·가독성·폰트·차트 범례·모바일 오버플로·지도 좌표 검수. 사용자 작업 흐름 E2E: 홈→기업→시설→근거→분석→보고서→내보내기.
## CI/산출물
`python -m unittest discover -s tests` 및 브라우저 테스트 명령, 실패 로그, 데이터 품질 리포트, 성능 결과, 수동 검수 체크리스트. 통과하지 못한 항목은 `PROGRESS.md`에 blocker로 기록.

## 공통 구현 규칙
- Python 3.11+ / SQLite(FTS5) / HTML·CSS·Vanilla JavaScript. 초기 로컬 개발, 이후 배포.
- 원본 명세는 `../ORIGINAL_kotra.md`; 이 패키지는 1~7단계 합의 사항을 반영한 개정 설계. 원본과 충돌하면 `MASTER_SPEC.md`의 결정 로그 및 본 문서의 명시적 계약 우선.
- 수집되지 않은 자료를 확보했다고 주장하지 말 것. 예시·테스트·합성 데이터는 실제 데이터와 물리적/논리적으로 구분.
- 기능 미구현 시 가짜 성공 화면을 만들지 말고 명확한 비활성 상태·오류를 제공.
- 모든 신규 데이터의 출처/수집 시각/검증 상태를 추적. 검증 불가 데이터는 탐색 가능하되 확정 사실로 표시하지 않음.
